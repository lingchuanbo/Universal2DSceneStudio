# 11 手动与 AI 双模编辑规格

> 产品要求：手动自定义编辑与 AI 驱动编辑是两条同等重要、共用同一工程数据的创作路径。不能把 AI 降为孤立聊天示例，也不能将其从首个可用产品版本中移除。本文定义基础 AI 编辑闭环；自动化生产、多 Agent 和视觉优化属于扩展能力。

## 1. 用户目标

用户可以通过节点、参数、关键帧和时间线精确编辑效果，也可以用自然语言创建新效果或修改当前效果。AI 生成结果必须是可读、可继续手动编辑的正常 Project/Processing Graph；手工修改的结果也必须能继续交给 AI 解释或迭代。两条路径不产生互不兼容的“AI 工程”和“人工工程”。

AI Provider 不可用时，手动编辑、保存、预览和导出仍须工作。AI 能力需要配置或选择用户授权的 Provider；不得暗中把工程内容上传到未经用户选择的服务。

## 2. 同一编辑器中的两条创作路径

```text
                     ┌─ 手动：节点 / 参数 / 时间线 / 关键帧 ─┐
Project + Selection ─┤                                     ├─ Edit Command/Patch
                     └─ AI：描述 / Plan / Preview / Apply ──┘
                                                              │
                                                    校验 + 编译 + 预览
                                                              │
                                              同一 Project Graph + Undo History
```

- Manual 路径直接编辑当前 Graph；所有有效改动均经相同的校验、Revision、Undo 和保存机制。
- AI 路径先产出受约束的 Plan/Patch，展示影响范围和预览，经用户 Apply 后以一个原子 Transaction 写入同一 Graph。
- AI Workspace 是编辑器中的可选工作区/侧栏，不是另一套项目、图编辑器或数据真相来源。
- AI 修改后，用户可直接拖节点、改参数或关键帧；手动修改后，用户可要求 AI 继续优化当前选择。不得要求重新导入或重建图。
- 当前选中对象、画布范围、播放头、可见错误/性能摘要可作为显式上下文；发送预览图、文件内容或其他敏感资产前按权限与隐私策略处理。

## 3. 基础 AI 编辑能力（可用版本要求）

1. **描述生成效果：** 根据用户目标、目标时长/画布和可用资产生成一个可编译、可预览、可手动编辑的节点图。复用已存在的节点组/模板优先于重复造图。
2. **修改当前选择：** 根据明确选择修改效果、节点或参数，如改颜色、速度、寿命、粒子数、拖尾宽度/渐隐、关键帧曲线。只修改达成目标所必需的部分。
3. **解释与确认意图：** 当对象、单位、范围或视觉目标不明确且会显著改变结果时，提出简短澄清问题；否则展示假设并给出可预览方案。
4. **给出修改摘要：** 应用前列出新增/删除/连接节点、参数旧值与新值、受影响对象、资源需求、风险、计算预算和已知限制。
5. **预览与应用：** Patch 在隔离预览中执行；无错误且用户确认后原子应用。用户可 Apply、Reject、继续对话迭代或在预览中调参数。
6. **沿用现有工作：** 可从当前节点/选中 Effect/当前工程上下文继续修改；图级目标不可实现时说明具体诊断，不能默默替换整张图。
7. **可回退与可追溯：** 每次 Apply 形成独立 Undo 步骤，并记录脱敏后的意图摘要（P0 默认不存原始用户 Prompt）、上下文摘要、Provider/模型、Patch digest、结果、Apply/Reject 和错误状态。

首个 AI 版本不要求任意代码生成、MCP、多 Agent、自动批量项目操作、自动导出覆盖、AI 贴图/视频生成或无人审核的生产变更。除非另有明确授权，AI 只能通过版本化 Tool API 修改结构化 Graph/Parameter，不执行 Shell 或任意文件操作。

## 4. 用户交互流程与状态

### 4.1 手动编辑

打开工程 → 选择 Effect/Graph → 编辑节点或属性 → 即时校验 → 预览/播放 → Undo/Redo → 保存/导出。离线状态不得隐藏或禁用手动功能。

### 4.2 AI 创建

描述目标 → 新建 Effect/Graph（初次创建尚无目标 Graph 时）或选择现有目标及约束 → 构造带 Revision 的最小上下文 → 生成 Plan/Patch → 展示假设与影响摘要 → Patch 校验/编译/预览 → 用户明确 Apply 或 Reject → 形成 Undo/Activity Record。

### 4.3 AI 修改现有效果

选择对象/节点/参数并输入修改指令 → 系统显示本次将引用的对象与上下文范围 → 生成 Patch → 与当前结果进行前后对比 → 用户确认后应用。用户能通过“只调整所选参数”“保留结构”等约束限制 AI 改动范围。

### 4.4 AI 结果状态

UI 至少可区分：`Idle`、`Planning`、`AwaitingClarification`、`PreviewReady`、`Applying`、`Applied`、`Rejected`、`Canceled`、`Failed`、`StaleRevision`。耗时任务可取消；取消或失败不留下半提交修改。预览状态与已提交工程状态有明显区别。

## 5. 共用修改与 Undo 契约

- Project Graph 是人工与 AI 共同的唯一事实来源。稳定 ID 与 Revision 用于定位对象和检查写入基础版本。
- 手动命令与 AI Patch 共用 Graph 校验器、编译器、运行时、Transaction Commit、Undo/Redo、dirty state 和序列化流程；可在 UI 层提供不同的交互入口。
- 每次改动均是原子命令/事务：成功则整体提交并增加 Revision；失败/拒绝/取消不改变 Project Graph 和保存状态。
- AI Patch 必须携带 `project_id`、`expected_revision`、`read_set`、`write_set`、目标 Entity/Node ID、操作列表、风险等级、资源预算、`requires_approval` 和预览/确认关联信息。Patch 操作使用受控的 CreateEffect/AddNode/RemoveNode/Connect/Disconnect/SetParameter/SetKeyframe 等结构化动作，不接受任意对象反序列化覆盖。创建新效果时由 `create_effect` 同时声明稳定 `effect_id` 和 `graph_id`，后续 Patch 操作只能引用该 Patch 创建的实体或当前工程中已存在的对象。结构草案见 [`schemas/graph-patch.schema.json`](schemas/graph-patch.schema.json)；该 Schema 不替代节点存在性、权限、Revision 和图语义校验。首版所有 AI Apply 均需要用户明确确认；低风险自动应用不属于 P0。
- Undo 以用户可理解的操作为单位。一次 AI Apply 默认是一个 Undo 单元；单纯在预览中反复试值不污染 Project Undo Stack。首次创建效果时，CreateEffect/CreateGraph 与后续节点/连接操作必须在同一 Patch Transaction 中提交或整体失败，不允许留下空 Effect/半张图。
- Undo 已提交 AI 改动后，AI Activity 记录保留并标明已撤销；Undo 不是删除审计历史。

## 6. 并发编辑与冲突

AI 计划/预览期间，用户可能继续手动编辑：

1. Patch 绑定生成时的 `expected_revision` 和它读取/写入的对象集合。
2. Apply 时 revision 未变化则正常校验并提交。
3. Revision 已变化时不得直接应用旧 Patch。对话仍保留，先读取受影响对象的最新值并显示过期提示。
4. 只有在 Patch 声明可重基、其读写集合与中途变更严格不相交、重基后的校验和预览均重新通过时，才允许展示“基于最新版本重新预览”。不得静默自动提交。
5. 写集合重叠、节点被删除/替换、连接或参数语义变化时，要求用户重新生成或选择明确的冲突解决方案。
6. 手动编辑发生在 AI Preview 之后、Apply 之前时，旧预览标记为过期并失效；Apply 按上述 Revision 规则处理。

## 7. AI 安全、权限与隐私

- 默认协作方式为先预览、后确认；删除节点/资源、覆盖文件、批量操作、改变全局设置和导出覆盖始终逐项或按明确批量摘要确认。
- 明确展示 Provider/模型、发送的数据范围及是否包含预览图/资产；Provider 不得在后台自动切换。云端模型授权与本地推理是不同选项。
- 上下文遵循最小必要原则，记录来源和 Revision；未被授权的工程资产不能为了“改善结果”自动上传。
- 对输出执行 Schema、权限、节点版本、连接类型、环路、预算和资源尺寸校验；模型提出的编译诊断/质量评价以软件验证为准。
- 限制单次 Patch 的节点数、操作数、纹理尺寸、粒子量、执行时间、显存/内存和预览时长；超限应返回用户可理解的原因。
- Provider 超时、拒绝、断网、格式错误或编译失败时，明确保留或丢弃草稿，不留下部分图修改。
- 工具调用和 Activity Log 不记录明文 API 密钥；日志内容按项目隐私策略可查看和删除。

## 8. 验收标准

### 手动路径

- 手动新建/修改节点、参数和关键帧后，可即时看到校验/预览结果，可 Undo/Redo、保存并重开。
- 手动工作流在无网络、未配置 AI Provider 或 Provider 故障时可完成。

### AI 路径

- 以固定工程和固定 Seed 测试至少三类任务：从空白生成粒子/拖尾效果、修改当前效果的参数/曲线、解释一项校验或性能问题并提供可应用修复。
- AI 生成修改是正常节点/参数/曲线数据；用户可在 AI Apply 后继续手动编辑并保存重开。
- Apply 前能看见改动摘要和可运行预览；Reject/Cancel/失败不修改 Project Graph，Apply 可整体 Undo。
- 指定节点/参数或“仅改参数不改结构”等范围约束时，Patch 不越权写入范围外对象。
- 用过期 Revision 测试时旧 Patch 必须被拒绝或重新预览，不覆盖用户的新手动修改。
- 模型无效输出、节点缺失、Socket 类型冲突、环路、资源超限和 Runtime 错误均有明确诊断且不产生半提交结果。
- 用户能识别当前是 Preview 还是已 Apply，能看到授权 Provider 及数据发送范围。

### 共用数据与追溯

- 同一 Graph 可在 Manual ↔ AI 之间无损切换；两种入口的更改经过相同校验、Revision、持久化和 Undo 系统。
- 双向接续测试必须通过：AI 生成 → 手动调参数/关键帧 → AI 再修改 → 手动连节点；以及手动创建 → AI 修改 → 手动继续编辑。全程不导出/导入中间工程，不丢节点 ID、资源引用或撤销边界。
- 保存并重开后，效果本体保持一致；AI Task Record 和事务历史足以追溯指令、Patch 及是否应用。

## 9. 能力分期

| 阶段 | 双模能力 |
|---|---|
| 垂直切片 | 验证 Manual 工程编辑/预览/保存和目标端导出；并贯通一个最小 AI 参数修改闭环：当前选择/Revision → Patch → Preview → Apply/Reject → Undo，证明能写入同一 Graph |
| 首个可用核心（P0） | Manual 全流程 + 基础 AI 创建/修改/解释、预览、确认、应用、撤销、Revision 冲突处理和 AI 记录；需要一个经批准且实际可用的 Provider 路径 |
| 扩展阶段（P1） | 多 Provider/本地模型路由、视觉模型 A/B 评估、性能优化 Agent、批量安全工作流、模板学习及更复杂的 Simulation Patch |

如产品商业策略或成本政策导致首个版本无法随附云端 Provider，仍需交付稳定 Provider Interface 和至少一种可实际使用的 AI 配置路径（本地或用户自带凭证）。不能仅以“架构预留”宣称已具备 AI 编辑能力。
